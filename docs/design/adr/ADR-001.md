# ADR-001: PostgreSQL as the database

- **Status:** accepted
- **Source:** T04-PA3 Section 3.6

## Context

ImpactHub stores accounts, roles, forum posts, campaigns, demo wallets and donations with many relationships. A donation must change the wallet, the donation records and the campaign total together or not at all (BR-11), and the campaign pages must answer within 3 s (NFR-01). C-01 names PostgreSQL, and only free tiers may be used (C-05).

## Decision

Use one PostgreSQL database on Render (free tier), normalised to 3NF (§5.3). Business rules that can be written as constraints are also enforced in the schema (CHECK, UNIQUE, FK; §5.2). Schema changes are made through versioned migration scripts in the repository.

## Alternatives considered

- MongoDB (document store): lost because the data is relational (user–role, campaign–review–donation) and multi-document transactions are harder to get right for BR-11.
- MySQL: also relational and would work, but it lacks the partial indexes and pg_trgm search used in §5.3, and C-01 already names PostgreSQL.

## Consequences

- + ACID transactions for the donation (BR-11) and constraints that catch invalid data even if a service has a bug.
- − Schema changes need migration scripts; the free-tier database has limited storage and connections, so the API uses a small connection pool (A-04).
- − The free Render PostgreSQL database expires 30 days after it is created (not covered by A-04): the production database is recreated from the migration scripts and seeded again (A-05) if it expires before the final demo (§3.5).
