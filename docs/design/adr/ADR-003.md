# ADR-003: JWT authentication with role-based access control

- **Status:** accepted
- **Source:** T04-PA3 Section 3.6

## Context

Every function except browsing needs login (BR-16), and each role may use only its own functions (BR-01, FR-01.4). Passwords must be hashed with bcrypt and protected endpoints must reject unauthenticated and unauthorized requests (NFR-02). C-01 names JWT with email and password.

## Decision

AuthService checks the password with bcrypt (work factor 12) and TokenService issues a signed JWT (HS256, valid 2 hours) that identifies the user. The Web App sends it in the Authorization header over HTTPS. On every protected route AuthMiddleware verifies the token and reads the user's current roles from user_role (one primary-key lookup) before it checks the required role; services also check ownership (BR-18). A role change (UC-15) therefore takes effect on the user's next request.

## Alternatives considered

- Server-side sessions: lost because sessions in memory are lost when the free-tier API restarts (OE-04), and sessions in PostgreSQL would need a session table, expiry cleanup and CSRF protection, while C-01 already names JWT.
- Roles carried in the JWT and trusted until it expires: lost because a removed role would stay usable for up to 2 hours, against FR-01.4.
- Google login (OAuth): F11 is Could-have and is not in the Must scope; email and password are fixed by C-01.

## Consequences

- + No session state on the server: a restart of the API logs nobody out; the same middleware protects every module; a removed role stops working at once (FR-01.4).
- − One indexed query per protected request; a stolen token stays valid until it expires, so it must be protected against XSS (React escaping, no HTML in posts).
