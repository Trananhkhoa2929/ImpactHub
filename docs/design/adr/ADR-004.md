# ADR-004: Store the campaign total and update it in the donation transaction

- **Status:** accepted
- **Source:** T04-PA3 Section 3.6

## Context

The amount raised and the progress bar must be correct right after each donation (BR-08, FR-05.2) without real-time push (C-04). A failed donation must change nothing (BR-11). The campaign list and detail pages must answer within 3 s at P95 (NFR-01).

## Decision

Keep campaign.amount_raised as a stored column. DonationService locks the wallet and campaign rows, inserts the donation, debits the wallet and adds the amount to amount_raised in one PostgreSQL transaction; any error rolls back all three. Every other write of a campaign row (edit, submit, close, automatic close, review decision) also locks the row first (CampaignRepository.findForUpdate; for the automatic close, findExpired locks the expired rows), so it cannot overwrite a total written by a concurrent donation.

## Alternatives considered

- Compute SUM(donation.amount) on every read: lost because the list page would aggregate the donations of every card on each request, which grows with the data (NFR-01).
- A materialised view refreshed on a schedule: lost because the total would lag behind (BR-08) and a scheduler is not reliable on a sleeping free-tier service (OE-04).

## Consequences

- + Constant-time reads of the total; one transaction keeps donation, wallet and total consistent.
- − The column duplicates data (a justified denormalisation, §5.3); concurrent donations to the same campaign wait for the row lock. The automatic close adds a short locking query to the list and detail requests; with FOR UPDATE SKIP LOCKED (findExpired) they do not wait for each other or for a donation. A PA4 test checks that amount_raised equals the sum of the donations.
